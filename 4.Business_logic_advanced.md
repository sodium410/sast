## Business Logic Vulnerability patterns  
Business logic vulnerabilities are flaws in application design and implementation that allow attackers to abuse legitimate functionality for malicious purposes.  
Characteristics: exploit legitimate functionality, hard to detect with scanners, business context, high impact, not in cve databases, unique to each app  
**Common patterns**  
Price manipulation - User controls price-related parameters that should be server-side only.  
Negatice quantity/price exploits - application doesn;t validate that quantities or prices are positive  
Integer overflow -- arithmatic operations exceed maximum integer size causing wraparound  - limit quantities  
Coupon/discount stacking abuse -- mulitple discounts applied when only one should be allowed  
referral/reward program abuse -- users exploit referral bonuses through fake accounts - accounts must be 24 hours old, users must verify email,;hone, referral limits, if already claimed,  
workflow/state machine bypass - users skip required steps in multi step process -- skip payment calling fulfill endpoint directly  

**Business logic testing methodology**  
identify business rules, map states, test edge cases - zero,negatice, decimal precision, rate limits, state transitions  

**Code Review checklist**  
Client controlled price  
no negative value check  
no overflow protection  
unlimited discount stacking -- multiple discount codes same order    
no state validation  
no uniquness - can claim multiple times  
no rate limiting  
Insufficient validation -- quantity high  
Think like an attacker  

**Race Conditions and Concurrency Issues**  
A vulnerability where the system's behavior depends on the sequence and timing of events that cannot be controlled.  
causing the application to behave incorrectly and bypass intended security or business controls.  
kind of business logic, need to identify impactful functions that can be a problem when requests collide  
Time of check TIme of Use  - where a condition is checked but the resource changes before its used  
example: check file exists, file replaced with malicioud file/file deleted, malicioud file sent or error  
Secure: Atomic operations --no check just try to use file handle is obtained and held  

**Database race conditions**  
double-spending attack -- User initiates multiple concurrent withdrawals before balance is updated.  
cause -- check and updates are seperate.  time of check and time of use creates a gap  
example: Send 5 concurrent requests to withdraw $100 from $100 balance  
all 5 read balance= $100 and All 5 subtract $100 Final balance= -$400 instead of $0  

Secure database transactions with locking  
Single atomic query with constraint update only if balance is sufficient  
cursor.execute(''' update users SET balance = balance - ? where id = ? AND balance >= ?''', (amount, user_id, amount)  
//this updates the balance, only if balance is more than amount requested  
SECURE: SELECT FOR UPDATE query locks the row # Other transactions must wait until this completes  
Transaction Isolation Levels -- read multiple available use the recommended based on the need  

**Inventory/stock management race conditions**  
Attack: 100 items in stock --> Send 10 concurrent requests for 15 items each -->All check: 100 >= 15 --> All subtract 15 -->Final stock = 100 - (10 * 15) = -50 ← Oversold!  
Secure: use atomic stock update with constraint - no check then use -- check use in one step

## File upload and Processing vulnerabilities  
File upload functionality is one of the most dangerous features in web applications when improperly implemented.  
Vulnerabilities in file upload can lead to remote code execution, stored XSS, denial of service, and full server compromise.  

Attacker uploads executable code (PHP, JSP, ASPX) disguised as legitimate file, then accesses it to execute code.  

**Checks**  
- No file type validation - validate file size  
- validate extension  - verify mime type by content - magic bytes  
- No path sanitization - never use user-provided filename - generate random filename -- prevents path traversal  
- verify path exists -- merge safe_file_name with upload folder -- and that folder should exist  
- verify size  
- store outside web root  - set read only perms for web server  
- store metadata in database  - validate file_id for path traversal  
- metadata stripped before download/serve  

**File extension bypass techniques**  
- double extensions shell.php.jpg  
- null byte shell.php%00.jpg  
- case manipulation -- shell.PHP, shell.PhP  
- alternate extensions -- shell.phtml, shell.php5, shell.phar   
- Mime type spoofing -- modify content-type header  
- Polyglot fles -- valid image+php code  -- try to open as image verify its actually an image img.verify() using magic and PIL import Image python modules  
  
**Polyglot uplaod prevention**  
- store outside webroot /app/storage/uploads - making it impossible to access them directly via a url
- rename uploaded files -- change the original filename to a random non executable uuid
- disable execution permissions - configure apache/nginx/iis to prevent script execution in the upload directory
- force content-disposition - serve files with content-disposition: attachment; filename='filename.jpg' to force a download instead of allowing broser to render the file mitigating any client-side script exectuions
- CSp - to prevent browser from executing scripts even if a polyglot is uploaded successfully
- deep content inspection -- clamav/yara rules whihc can iden signature of hidden code within images
- Re-encode images - use libraries like imagemagick to re-process and save uploaded images - this process typically strips xif data, comments and any appended malicious code
- content disarm and reconstruction(CDR) - use cdr to rebuild files enuring safe expected content is retained stripping polyglot payloads

**Known vulnerabilities**  
Imagetragick with Imagemagic -- gives RCE  
Zip bombs - small compressed file expands to huge size causing DOS  

**File Storage best practices**   
- Store files outside web root -- not accessible via URL
- Randomize filenames  -- use uuid
- Server via controller not directly --- /download?file=1f34fs  instead of direct /uploads/file.pdf
- Set content-disposition header --  content-disposition: attachment -- allows file downlaod instead of rendering it in browser
- Seperate storage by sensitivity
- Use object storage for production -- s3, blobs, gcloud instead of local filesystem

**Secure file serving** -- validate filename, check authorization, verify file exists, set secure headers, prevent caching, set content-type based on mime, prevnet xss via content-disposition, additional x-content-type options

-- no size limit
